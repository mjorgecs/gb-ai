# The Prompt

This section of the report addresses the initial prompting phase and its subsequent refinement process. The user submits the initial prompt through a chat interface, which supports both a free-text description of the intended application and the upload of supplementary files containing detailed requirements (e.g., a document specifying business rules or a reference design). Additionally, a planning-step option must be clearly visible within the interface, allowing the user to choose between generating the application immediately or first collaborating with the Description Agent (DA) to plan the application's structure and functionalities in greater detail.

During the planning step, the user engages in an iterative dialogue with the DA in order to produce a highly detailed document describing the application's purpose, structure, requirements, and intended functionalities. Beyond serving as the direct input for the current implementation stage, this document has value as a standalone artifact: it can later be reused to describe the application to any other AI-powered No-Code App Builder platform, attached to the application's internal documentation for future reference, or shared with a development team as a functional specification, in case the project needs to be transferred or expanded beyond the platform itself.

To guide users and illustrate the platform's capabilities, a curated library of pre-made prompts must be made available. As is already the case with the extension-builder AI, this library should offer a selection of prompts corresponding to the most common and useful application types — for example, "restaurant reservation app with online menu and table booking," "personal portfolio website with a project gallery," or "event registration platform with ticketing and attendee check-in." Beyond providing inspiration, this library also serves to increase user engagement with the platform by lowering the barrier to entry for users who are unsure how to begin describing their idea.

# The Refining Process

Once the DA has analyzed the initial prompt, it returns a detailed characterization of the application, comprising the following elements:

- **Application type and purpose:** The DA's response must include its interpretation of the application and its underlying objectives, presented as a concise summary. This allows the user to validate the interpretation, correct any misunderstanding, or supply additional context.
- **Design options:** Key design decisions — such as color palette, general UI format, and typography style — must be clearly explained to the user. Beyond informing the user of the choices made, this explanation serves an educational purpose, helping the user understand the reasoning behind each decision and keeping them actively engaged in the process. For this reason, the explanation must be clear, accurate, and genuinely informative rather than purely technical.
- **Sections:** As the sections directly reflect the structural organization of the application (e.g., home, catalog, chat), they must be explicitly listed and recommended based on the application's stated requirements.
- **Extensions:** Extensions represent optional but valuable services that enhance the application's functionality (e.g., a chatbot, push notifications, or payment processing). They should therefore be proposed during the description stage, with a clear explanation of the purpose and benefit of each one, so the user can make an informed decision about which to include.

Based on this initial detailed characterization, the DA must also recommend the most suitable pre-made layouts available on the platform. Doing so encourages greater reuse of existing, already validated application templates, which in turn improves consistency and reduces implementation risk.

Following the agent's response, the user may continue to iterate with the DA, refining and expanding the description until it accurately represents their intended application. Since users can also modify the application generated by the Implementation Agent (IA) directly after creation, the transition from the description stage to the implementation stage does not need to happen at a single fixed point — several models can govern when this transition occurs:

**1. User Authorization**

Under this model, the user has an unrestricted number of iterations with the DA in order to reach the most representative possible description. Only once the user is satisfied does the user personally authorize the transfer of the specification to the IA for implementation.

- **Advantages:** This approach maximizes the accuracy and completeness of the final description, since the user retains full control over when the application is ready to be built. It also reduces the likelihood of wasted implementation cycles, as the IA only begins work once the specification has been explicitly validated by the user.
- **Disadvantages:** The absence of a limit on iterations can lead to a slower process, potentially frustrating users who expect quick results. It may also result in higher token consumption due to an open-ended number of refinement cycles, and, for some users, can lead to decision fatigue when faced with unlimited opportunities to keep refining.

**2. Limited Iterations**

Under this model, the user is granted a fixed, limited number of iterations with the DA. Once this limit is reached, the DA finalizes the description and automatically forwards it to the IA for implementation.

- **Advantages:** This approach produces a predictable and bounded cost and latency profile, which simplifies resource planning. It also encourages users to be more precise and deliberate in their initial prompt, and works particularly well in combination with the pre-made prompt library, which is designed to yield strong results within a limited number of refinement steps.
- **Disadvantages:** The iteration limit may be reached before the description is fully representative of the user's intention, particularly for more complex applications, increasing the risk that the generated app does not match expectations. Users may also perceive the fixed limit as rushed or overly constraining, especially expert users accustomed to iterating freely on traditional no-code platforms.

**3. DA's Autonomous Decision**

Under this model, the DA independently determines when the description is sufficiently complete and instructs the IA to proceed with implementation, either with or without requiring explicit user approval beforehand.

- **Advantages:** This approach offers the most seamless and frictionless experience, particularly for non-expert users, by minimizing the cognitive load associated with managing the refinement process. It also enables faster application delivery for common, well-understood use cases that closely match the platform's pre-made prompt library.
- **Disadvantages:** There is a meaningful risk of the DA triggering implementation prematurely, before the user actually intended to finalize the description, which can undermine user trust in the system. Reliably estimating when a description is "good enough" is also a non-trivial technical challenge, and removing the user from the final decision — particularly for expert users — may be perceived as a loss of control over a process they are otherwise capable of managing themselves.
